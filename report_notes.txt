MPI_Gather on 2D Torus - Report Notes

1. Project Goal

The goal of this project is to simulate MPI_Gather communication on a 2D Torus topology using OMNeT++. The selected collective communication operation is MPI_Gather, and the selected topology is 2D Torus. The performance of a topology-aware optimized gather algorithm is compared against a naive gather approach.

In MPI_Gather, every non-root process sends its local data to a root process. At the end of the operation, the root process holds the data from all participating processes.

2. Topology

The simulated network is a 2D Torus. Nodes are arranged in a two-dimensional grid. Unlike a simple 2D mesh, the edges wrap around. Therefore, the leftmost and rightmost nodes in each row are connected, and the top and bottom nodes in each column are connected.

The experiments were performed for:
- 4x4 Torus: 16 nodes
- 8x8 Torus: 64 nodes
- 16x16 Torus: 256 nodes

The root node is rank 0 in all experiments.

3. Algorithms

3.1 Naive Gather

In the naive approach, every non-root node sends its data directly toward the root node using shortest-path routing on the 2D Torus. This approach is simple, but it creates high traffic around the root because every node eventually sends a separate packet to the root.

3.2 Optimized / Topology-aware Gather

In the optimized approach, the gather operation is performed in two phases.

Phase 1: Row-level gather
Each row first gathers its data at the row leader. The row leader is the node in the same column as the root.

Phase 2: Column-level gather
After each row leader collects the data of its row, it sends one aggregated packet to the root.

This method reduces the number of packets received by the root and decreases total hop transmissions. However, row leaders must wait until they collect all row data before sending aggregated packets to the root. Therefore, completion time may increase slightly.

4. Simulation Parameters

Root rank: 0
Payload size: 1024 bytes
Link delay: 1 ms
Link datarate: 10 Mbps
Start time: 1 s

6. Analysis

The optimized algorithm successfully completed the gather operation in all tested topologies. This is verified by the root received payload count. For 4x4, the root received 15 payloads; for 8x8, it received 63 payloads; and for 16x16, it received 255 payloads.

The optimized algorithm significantly reduced total hop transmissions:
- 4x4: from 32 to 20
- 8x8: from 256 to 144
- 16x16: from 2048 to 1088

The optimized algorithm also reduced the number of packets received by the root:
- 4x4: from 15 to 6
- 8x8: from 63 to 14
- 16x16: from 255 to 30

This shows that the topology-aware approach reduces both network traffic and root load. The improvement becomes more visible as the topology size increases.

However, the completion time increased slightly in the optimized approach:
- 4x4: from 1.0197344 s to 1.025192 s
- 8x8: from 1.0698528 s to 1.093152 s
- 16x16: from 1.2660112 s to 1.3551616 s

This happens because row leaders wait to collect data from their rows before sending aggregated packets to the root. Also, aggregated packets are larger than individual packets, so they may take longer to transmit. Therefore, the optimized method improves traffic and root load, but introduces aggregation delay.

7. Conclusion

The simulation results show that the topology-aware MPI_Gather algorithm is more efficient than the naive approach in terms of total hop transmissions and root load. The optimized algorithm reduces unnecessary traffic by collecting data at row leaders before forwarding aggregated packets to the root.

The main trade-off is completion time. In these experiments, the optimized algorithm has slightly higher completion time because of row-level aggregation delay. However, as the network size increases, the reduction in total hop transmissions and root load becomes more significant.

Therefore, the optimized approach is useful when reducing network traffic and avoiding root bottleneck are more important than minimizing only the final completion time.
